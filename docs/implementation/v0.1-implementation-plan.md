## B. Proposed end-to-end architecture

Accepted data/ownership direction, with the v0.1 processing order made explicit:

```text
Existing Linux sources
  -> C++ adapters: native ingestion/validation + bounded per-event context
  -> C++ normalization + outgoing contract validation
  -> Unix domain socket / JSON Lines
  -> Python normalized-event validation and processing
  -> Python-owned SQLite event persistence
  -> deterministic detection on that one event
  -> Python-owned individual alert persistence
  -> authenticated localhost FastAPI
  -> React/TypeScript dashboard (accepted Vite/SSE direction)
```

The collector and Python backend remain separate processes. Initially Python's
receiver, writer, detector and API are modules of one service, not independent
network services. Python can enrich using already authorized application context;
it must not independently read `/proc`, journal or Audit. Native OS work and eventual
normalization stay in C++. Rules stay separate from engine implementation.

| Boundary | Necessary checks / consequence |
|---|---|
| Linux native input -> C++ | Untrusted lengths/types/messages; retain useful native meaning, source identity and diagnostics; avoid blocking other sources |
| Collector -> Python | Treat even an authenticated peer's payload as untrusted; enforce frame/schema/version limits independently on both sides |
| Python -> SQLite | Only designated Python writer paths write; parameterized queries, bounded transactions and deduplication; handle unavailable storage explicitly |
| API -> browser | Root-only backend authentication/authorization on every sensitive endpoint, including health/SSE; localhost is not authentication; untrusted content rendered safely |

### First-run control flow — separate from event data flow

The accepted product sequence is metadata-only source discovery → scoped access/
capability/possible-field assessment → explained recommendations and draft source
configuration → explicit authorized confirmation → initialization of selected
collectors → actual runtime health/field assessment. These are separate logical
operations and interfaces; they do not mandate new processes or a finalized wire
protocol. Static support, selected configuration and runtime success must not share
one availability boolean.

Before confirmation, no subscription, event-reader initialization, security-log
payload sampling or unrelated `/proc` context inspection is allowed. Assess field
possibilities from documentation or scoped prior authorized evidence and label
actual current field presence Unknown until collection is confirmed. A bounded
sample can be read-only yet still be collection. Actual service identity/access
must be checked without root retry; no known blocking condition is a prerequisite
for preselecting a source as usable. Eligibility/recommendation details remain
D-14 design work and never guarantee initialization or delivery.

Backend and C++ orchestration must enforce confirmed recognized-source choices,
not trust browser checkbox state or a forged control call. Selected initialization
may fail; report that failure, preserve the working confirmed subset and authorized
history/configuration access, and never auto-enable newly discovered or unselected
sources. No-source-selected is an explicit non-collecting state, not healthy
monitoring. The current adapter's start/poll API is only a mechanism; it does not
implement the application consent gate.

Selection changes HIDS-owned configuration/collection only, never journald/PAM/
auditd settings, Audit rules, kernel settings, packages or privileges. Confirmation
persistence, later edits/retries and boot resume are unresolved (D-14). No initial
confirmation may be presumed. A fixture-only M1 harness is not OS event collection
and need not wait for the entire onboarding UI; enforce/test the gate before any
live-source integration in M2/M3.

**Recommended thin-slice order:** join a fixture-backed C++ producer to receipt,
SQLite and a protected read path before adding every adapter or elaborate UI. A
fixture slice is integration evidence, not real-source monitoring. Its contracts
must be reviewed as a limited pilot; do not turn placeholder values into production
defaults. Complete v0.1 still requires real supported process and existing-log events,
a one-event rule and root-only dashboard/health use on Ubuntu.

## C. Process collection

The accepted provisional direction remains [ADR-006](../decisions/006-provisional-process-collection.md):
cn_proc live lifecycle plus best-effort `/proc` context. Do not copy the research
program's child creation, stdout report, one-hour test lifetime or child-only filter
into a production service. The native adapter is already a separate implementation.

### Subscription and lifecycle

One serialized owner calls start/poll/stop. LISTEN is sent once per explicit session;
ACK success and observed event delivery are independent facts. The source may stay
unconfirmed without an ACK because filtered ACKs can be suppressed. Preserve FORK,
EXEC and EXIT native kinds, thread ID versus TGID, event-supplied parents, CPU,
per-CPU sequence and monotonic timestamp. An EXEC event does not supply a parent;
do not fill one as though it did. Raw EXIT encoding is not automatically a shell
exit code. The local adapter session is not a global process or boot identifier.

The research run's three child events and two aggregate discontinuities remain in
[the research record](../research/process-connector.md#sequence-discontinuity-investigation).
First samples on a CPU establish a baseline. A sequence discontinuity is not an
exact loss count; it may involve filtered types or undisplayed traffic. No further
kernel run is needed to change or explain away the reported number.

### Proposed best-effort enrichment

Add an injectable, bounded C++ context reader before final normalization. Start
with process name, executable path, selected identity fields and start information
only where justified; use fixtures first. Arguments need separate sensitivity,
length/redaction and retention review; do not collect environment variables by
default. Preserve source path versus resolved executable distinctions observed in
research. Missing access or an already-exited process must not discard the native
event or fabricate an empty executable, UID zero or parent.

Use native IDs plus available boot/start observations to check PID-reuse races;
compare before/after context where feasible. This reduces misattribution but does
not make separate `/proc` reads atomic or guarantee short-lived process context.
Record observation time separately from event activity time and classify gone,
inaccessible, incomplete and unknown results. Do not build a process history graph,
match related events or query prior event history for v0.1 enrichment. Parent IDs
already provided by one native record are per-event context.

### Loss, shutdown and recovery

ENOBUFS/overrun/truncation and malformed inputs must leave inspectable incomplete-
interval diagnostics. Later delivery may show the source returned, not that earlier
coverage was repaired. The implemented sticky degraded flag is useful; service-level
scheduling, health freshness and source reassessment are still missing. A bounded
scheduler must prevent journal reads, enrichment, transport or one failing adapter
from starving the others (D-10).

Shutdown cancellation reaches the serialized owner; stop accepting work, bound drain
policy, attempt one explicit IGNORE and close. Never call adapter operations from
signal handlers. No final IGNORE ACK is assumed. Record unsubscribe failure without
pretending kernel completion is verified. Crash/SIGKILL cannot guarantee cleanup.
No initial subscription may begin before confirmed selection, including one used
as a hidden preflight capability probe. No automatic kernel resubscription/root
retry should be introduced while installed-
kernel cleanup behavior and a deliberate recovery policy remain unresolved. IPC
reconnection is a different mechanism and must not repeatedly recreate the kernel
subscription. Live service-account validation is a separate approval gate, not
performed in this review.

## D. Authentication and system-log collection

Use the existing [authentication research](../research/authentication.md) rather
than assuming a generic Linux authentication log format.

| Source / observation | Intended v0.1 use | Missing evidence / implementation consequence |
|---|---|---|
| Journald, sudo | Existing PAM failure/session and command-request context | Original successful-record layouts, exact keys/types and timestamps incomplete; a sudo request is not proof of child execution or completion |
| Journald, SSH | Failure/success, password method, client address/port and session-opening context | `_COMM=sshd` missed `sshd-session`; complete structured fixtures and broader method/version behavior remain pending |
| Existing Linux Audit | `USER_AUTH`, account/credential/session events as complementary security records | auditd was active in one research VM with no explicit rules; this is not a default-installation or syscall-execution coverage guarantee |
| Existing system journal records | Supported service/system-log categories with bounded selection and native provenance | Choose actual event families/fixtures; do not ingest the entire journal just because it is readable |

**Recommended implementation order:** a narrow journald authentication dataset,
then selected existing system records; add the existing Audit read path where
available without making it a mandatory installation dependency. The native journal
API is the established direction. Its documented access scope depends on readable
journal files/namespaces, not successful creation of a handle alone.
[systemd 259 journal API](https://www.freedesktop.org/software/systemd/man/259/sd_journal_open.html).
If development headers/libraries are missing, record the limitation and request
approval rather than installing packages or silently choosing a different production
collection design. Python does not become the fallback OS collector.

Only after selected-source confirmation (or separately explicit research authorization)
may the application inspect security-event payloads for observed-field assessment.
Preflight metadata/access checks must not turn into a journal sampling reader.
Capture representative sanitized fixtures in a separately authorized read-only
research step before declaring supported mappings: positive/negative, incomplete,
repeated keys, binary/oversized text, unexpected formats, duplicate retrieval,
rotation/restart and inaccessible-source cases. Research summaries already committed
are not complete raw parser fixtures. Investigate actual service identities rather
than assuming interactive/root access carries over. Journal-group grants can expose
much more than the intended dataset and require least-privilege review.

### Record boundaries and duplicates

The three SSH journal selectors overlap: deduplicate copies of the same source
record using proven source identity, not a guessed semantic fingerprint. PAM failure
and Failed password messages appear to describe one attempt but are distinct records;
preserve both and do not count them as independent attempts. v0.1 may categorize
them individually with source limitations, not fuse them into an authentication
sequence or cross-source evidence alert. Avoid duplicate alerting on retransmission
of the identical event; this is transport/source deduplication, not activity correlation.

Audit serials 407–411 in the sudo research identify separate events, not one
multi-record event or five commands. Group native records only when the source
actually defines one event; any grouping needs bounded memory/time and incomplete-
group handling. Keep audit login UID/session, process credentials, authenticated
account and target account distinct. Grantors `?` is unresolved, not an invented
principal. The SSH logout error remains unresolved and must not become a failed-
closure finding. Independent normalized-event relationships are v0.2 work.

Use an already available Audit log/read interface; never claim the kernel Audit
stream or add rules/dispatcher configuration. Missing package, unavailable read
path, denied access and no matching records need different evidence/status. Existing
log-file rotation, cursors, checkpoints, redaction/retention and replay limits need
source-specific design (D-10/D-11); restoration of access is not promised backfill.

## E. Initial event envelope — proposal, not a contract

The following are **logical information groups**, not JSON keys or mandatory ECS
fields. The [schema draft](../event-schema.md) remains the reference for candidate
mapping; no custom namespace, `hids.*` path or executable JSON Schema is approved
by this plan.

| Logical group | Proposed information and handling | Open choice |
|---|---|---|
| Contract metadata | ECS reference and HIDS contract versions tracked independently; native source/version provenance | Version identifiers, compatibility and unknown-field policy (D-02) |
| Event identity | Stable identity retained through retries, storage, alert linkage and display | Collector-assigned opaque ID before send versus source-derived identity where adequate; scope/collision/crash behavior (D-03) |
| Source provenance | Adapter, source-native type/code, original source record identity where available, collection session and optional boot context | Exact source-key construction and retention; no global ID from PID/sequence alone |
| Native lifecycle | PID/thread ID and TGID, available parents, CPU, sequence, raw EXIT values with meanings retained | ECS role mapping and native/unmapped representation |
| Available activity time | Reliable source wall time with provenance, precision and trust limitations | Missing/unreliable-time representation and acceptance (D-04) |
| Native monotonic time | Raw cn_proc `timestamp_ns` with units/clock and available boot scope | Separate native field/group or protected source reference; never Unix epoch or invented `@timestamp` |
| Collection time | Collector observation time, clearly labeled as observation | Clock representation, rollback/error handling; not an activity-time fallback |
| Processing/storage time | Python receipt/commit observations when justified | Distinguish backend receipt from durable storage; exact normalized fields remain open |
| Per-event context | Justified best-effort `/proc` results with observation/access/race limitations | Allowlist, redaction and privacy policy; do not retain every candidate value (D-05) |
| Native originals | Useful bounded native information or protected source reference, preserving original event type | Typed structure/reference versus approved text; `event.original` is textual, not an arbitrary structured container |
| Collection diagnostics | Separate status/diagnostic observation tied to source/session | Dedicated control frame versus a separately versioned event family (D-02/D-06) |

**Completed M1 pilot:** carries one synthetic native EXEC record, its provenance/
identity, raw monotonic time and explicit observation time without claiming wall-clock
activity time, as specified in the [approved limited contract](m1-pilot-contract.md).
A later authentication fixture should contrast genuine source wall time; it is not
an additional M0/M1 gate. Supported records must survive round-trip validation with
missing values explicit. Source
zero/sentinel values remain distinguishable from an actual known parent/identity;
never create semantic zero/empty-string defaults for missing information.

ECS candidates such as `event.id`, `event.code`, `@timestamp`, `event.created` and
`event.ingested` require their pinned meanings; they are not an excuse to map every
native field immediately. See [ECS 9.5.0 event definitions](https://github.com/elastic/ecs/blob/v9.5.0/schemas/event.yml).
Do not add a production contract or a reliable wall-time conversion until D-02–04
are resolved. A calibrated clock-pair observation could support a future conversion
with stated error/boot/suspend limits; it is not authorized fallback behavior.

Reject identity collisions where the same proposed ID accompanies different event
content rather than overwriting prior meaning. A content hash alone cannot tell
repeated identical activity from redelivery. Keep one alert's triggering-event/rule
link; none of these foundations requires an evidence graph or cross-event detector.

## F. IPC design — accepted Unix socket and JSON Lines, details proposed

A Unix domain socket and JSON Lines remain accepted. **Recommended pilot:** a
pathname `SOCK_STREAM` endpoint owned by the Python receiver and one serialized
C++ sender, with transport I/O isolated from source polling. Socket type, path,
ownership and scheduling still require D-01/D-06 approval. Stream sockets provide
bytes rather than application records, so JSON Lines must supply the framing.
Path permissions and Linux peer credentials can enforce local peer policy;
[Linux Unix socket reference](https://man7.org/linux/man-pages/man7/unix.7.html).
No TCP/message-broker replacement or public/debug event stream is proposed.
No JSON codec/validation dependency is currently declared in the repository.
D-13 must review the C++ codec and Python validation approach/versions before this
production slice; do not substitute ad hoc string concatenation/escaping or
assume the required packages are installed simply because GCC tests passed.

| Concern | Proposed behavior to validate before adoption |
|---|---|
| Connection lifecycle | Backend listens in an application-owned protected runtime directory; collector connects only to the configured trusted path, verifies expected peer identity, and reports disconnected/connected states |
| Framing | One bounded UTF-8 JSON object per newline; escape embedded newlines/binary data using approved representation; handle several frames per read and one frame split across reads |
| Partial I/O | Maintain bounded byte offsets on writes, tolerate short writes/reads and EINTR/EAGAIN, handle peer shutdown mid-frame; ignore SIGPIPE through application-level ownership or use appropriate send flags |
| Validation | C++ validates outgoing normalized contracts; Python independently checks framing, types, versions, source roles and size/depth; neither trusts the other endpoint to validate for it |
| Invalid input | Define permanent rejection versus transient storage failure; discard/quarantine only bounded approved metadata, never log whole sensitive payloads; fail a connection safely on over-limit/ambiguous framing |
| Resource limits | Candidate pilot maximum 64 KiB per frame plus bounded queue/connection/depth limits; all numbers provisional until source distributions and privacy are reviewed; do not silently truncate semantic fields to fit |
| Backpressure | Bound producer queue and backend work; keep native collection/health responsive. If a limit forces local loss, record measured local drops and an interval limitation, not a guessed kernel-loss count |
| Peers/permissions | Only designated identities may traverse/connect; receiver checks peer credentials and sender checks server identity as appropriate; filesystem names alone do not authenticate a peer |
| Shutdown | Stop intake, drain within an approved deadline or report abandoned work, preserve approved pending state, close IPC separately from serialized connector IGNORE |

### Durability, acknowledgements and reconnect tradeoff

Compare send-only delivery (cannot prove receipt), receipt ACK (cannot prove durable
storage), and durable-event-commit ACK. **Recommendation:** the latter for the pilot,
with stable event IDs and deduplication across retry. Application ACKs here are
unrelated to cn_proc LISTEN/IGNORE ACKs. Exact frame names, correlation tokens,
version negotiation, rejection responses, queue sizes and deadlines remain open.

A lost commit ACK can cause redelivery; deduplicate the event without rerunning a
completed identical rule finding. Do not advertise exactly-once transport. Proposed
reconnect is bounded/backed off for IPC only, preserving pending event identities;
it must not repeatedly LISTEN/IGNORE or alter logging sources. Kernel reconnect
policy requires its own gate. Establish startup ordering, stale-socket handling
(check ownership/type; never unlink arbitrary files), endpoint replacement and
shutdown tests before exposing the service.

A bounded RAM queue is simple but loses pending events on collector crash. Protected
bounded spooling can improve retained-event retry but adds disk permissions,
redaction, retention, corruption and crash-recovery obligations. Decide D-06/D-09
before claiming durability across producer restart. Journal replay may exist only
within retained records/checkpoint semantics; cn_proc cannot replay past events.
The backend's accepted-event ACK must not claim a successful detector, an alert,
source completeness or a repaired historical gap.

## G. SQLite storage — proposed minimal v0.1 model

Python owns all SQLite writes, migrations, retention and alert persistence.
C++ has no database access requirement. The initial logical model below does not
approve DDL, field paths, key types, tables or retention defaults (D-07/D-09).

| Logical record | Minimum responsibility | Boundaries |
|---|---|---|
| Individual event | Stable identity, contract versions, useful searchable normalized fields, bounded native/provenance representation and truthful times | Distinguish native versus enriched values; preserve unknowns and source clock; no universal fabricated activity timestamp |
| Individual alert | Identity, one triggering-event reference, rule identifier/version, deterministic matched condition, severity/limitations and creation observation | No multi-event `alert_events`, relationship manager or evidence aggregation |
| Rule identity/configuration | Approved rule ID/version and semantics needed to interpret old findings | Exact rule file format is unresolved; a current rule label alone cannot rewrite historical meaning |
| Source status/checkpoint | Last assessed source state, evidence/reason/freshness and supported source progress | Checkpoints are source-specific; no resume cursor or guaranteed backfill for cn_proc |
| Schema migration state | Ordered applied migrations and compatible versions | Never silently reinterpret persisted events; migration metadata is not a new security event schema |

**Recommended processing model:** persist each independently validated event first,
then evaluate approved rules on that same event and write idempotent individual
alerts. Track per-event evaluation pending/completed/skipped/error so a backend
restart can resume that work without using other events to establish a match.
This is operational replay of one record, not time-window/sequence detection.
The durable-event ACK in F confirms only event storage. Detection exceptions must
not silently delete accepted events or convert a failed evaluation into no match.
An alternative single transaction for event plus evaluation requires an explicit
policy for rule failure and latency; it is not silently selected here.

A candidate alert uniqueness key is triggering-event identity plus rule identity/
version for a completed deterministic evaluation. Exact constraints and rerun policy
need review. Event re-delivery does not automatically create another alert; a
changed payload under an existing event ID is a collision/error, not an update.

Retain accepted WAL, appropriate indexes, configurable retention, bounded growth,
deduplication and migrations from [ADR-002](../decisions/002-sqlite-storage.md).
Candidate indexes cover event identity, storage/observation ordering, supported
source/type/time filters and each alert's event/rule link. Do not index every
native value or add text-search dependencies before requirements justify them.
Pagination must be bounded and deterministic even when activity time is absent;
choose explicit observation/storage ordering and label it in the UI.

Database, WAL/SHM sidecars, spool, exports/backups and temporary data need equivalent
privacy controls. WAL is not a replacement for bounded checkpoint/retention and
busy-reader handling; the [SQLite WAL documentation](https://sqlite.org/wal.html)
describes sidecars, checkpointing and reader/writer behavior. Put validation/run
state on the VM's private local filesystem, not the macOS VirtFS transfer share;
shared source transfer is not an approved production database/IPC location.

Test short transactions, bounded SQLITE_BUSY retries, disk full/read-only/corrupt
storage, migration failure, interrupted commits and crash recovery. If an event
cannot be committed, do not send a durable ACK; backpressure plus health must
expose the failure. Keep a bounded independent health path so a broken database
does not make its own failure invisible. Preserve already-readable history when
possible without promising availability if the database itself is corrupt.

Retention must preserve interpretable alert-to-triggering-event links. Choose a
coherent removal/expiry policy and make unavailable/expired evidence explicit;
never leave a resolved-looking fabricated event or claim indefinite history while
bounding disk. Choose protected backup/rollback behavior before migrations and
avoid automatically deleting user data to recover from an unknown failure.

## H. Detection engine — individual events only

The minimum detector takes one validated event with its already-authorized
per-event context and one approved rule definition. It produces match/no-match/
unable-to-evaluate/error with a reason, not a confidence score. Required/Important/
Optional evidence remains rule-specific, sensitivity independent. A missing required
field must not become a negative safety verdict.

Initial candidates, not finalized rules or severities:

- Recognize/categorize an individual authentication failure only from a validated
  source meaning/outcome; one failure is not evidence of malicious intent.
- Match one process EXEC event against a simple configured condition if required
  executable/context information is available. An executable-path rule cannot
  run from cn_proc IDs alone, and a sudo command-request message is not an EXEC.
- Categorize supported system records without claiming every informational record
  deserves an alert. Rule definitions determine which findings create alerts.

Every alert identifies the rule/version, its one triggering event and the condition
that matched, with source provenance and relevant missing-data/benign explanations.
Keep rule files under `rules/` separate from engine code. YAML remains a proposal;
start with a small declarative, bounded predicate set after D-08 review. Do not
provide arbitrary Python/shell execution or unbounded user-supplied expressions.

Tests: a complete positive fixture, a complete negative fixture, missing/incorrect
field roles, unknown outcome, duplicated transport event, malformed contract,
rule exception, disabled rule and changed rule version. Assert one event alone is
passed into evaluation; no detector query retrieves other events/history. No
threshold across events, repeated-failure counting, failure-then-success sequence,
process-behavior sequence, cross-source fusion or multi-event supporting evidence
is part of the v0.1 interface. Severity describes potential impact, not certainty.

## I. Minimum dashboard and API

FastAPI plus React/TypeScript/Vite and SSE remain accepted. Design root-only
authentication/authorization **before** exposing sensitive routes (D-01/D-12).
No temporary unauthenticated local dashboard is an acceptable integration shortcut.
Backend checks protect discovery/configuration, events, alerts, health and SSE,
not merely frontend navigation. The usability goal for ordinary computer users
is not broader human access eligibility.

Use [product experience](../product-experience.md#proposed-navigation-and-progressive-disclosure)
for the proposed Overview, Alerts, Activity, Sources, System Health and Settings
navigation. Overview is the default landing page. Its central alert feed must sort
severity first, recency second. Proposed Critical / Emergency, High, Moderate, Low
and Informational labels are not finalized rule severities or ECS values (D-08).
The recency clock/stable tie-break remain explicit D-04/D-08 choices; do not invent
missing activity time or silently map historical Medium examples to a new band.

| View / flow | Minimum behavior | Explicit limit |
|---|---|---|
| Sources / first run | Metadata-only discovery/assessment, explained usable recommendations, individual draft choices, confirmation and selected-versus-runtime status | No subscriptions, reader initialization or payload sampling before confirmation; selection never changes OS logging/configuration |
| Overview / Alerts | Severity/recency feed and one-event rule/condition/trigger traceability with concise health warnings | Ordinary collected events belong in Activity; operational notices need not be security alerts; no confidence/suspiciousness scoring |
| Activity | Bounded searchable/filterable pages and individual detail; truthful time/identity/provenance/missing-context labels | History date filtering is not time-window detection; no process graph or richer behavioral timeline |
| System Health | Source failures, queue/receiver/DB issues and freshness with clear explanations | Quiet/selected/statically supported is not proven runtime health; no coverage/confidence percentage |
| Settings / technical details | Approved HIDS-owned preferences; progressive disclosure of native fields/errno/diagnostics | Same backend authorization as primary UI; no arbitrary shell/SQL/filesystem or OS administration |

Recommendations/defaults are explained and editable; confirmation is enforced
server-side, not by a button alone. A selected source that fails remains visibly
failed while other confirmed sources and retained history/configuration remain
usable. No selected sources means monitoring is not collecting. Prototype first-run
UI against fakes before separately authorized live adapters. Detailed persistence,
edit/retry and restart consent policy is D-14, not a frozen settings schema.

Recommend limited polling/SSE for changes with explicit disconnect/staleness and
session-expiry behavior; define synchronization without promising source backfill.
Escape collected text and limit pages/filters. Progressive disclosure reduces
technical clutter but must not conceal essential failures or expose unauthenticated
technical endpoints. No elaborate visualizations or v0.2 evidence relationships are
required. Severity is potential impact, not certainty of malicious intent.

## J. Security and privilege separation

### Identity/permission matrix — proposals, not grants

Names below describe logical roles. Exact accounts/groups, paths/modes, service
units and minimum capabilities require owner approval and tests under those actual
identities. This review creates no accounts, changes no memberships and runs no
probe as a new identity. Unprivileged collector/backend are the preferred baseline;
root is not the default remedy for denied access.

| Component / resource | Recommended baseline | Permission to justify/test | Denied-access or compromise boundary |
|---|---|---|---|
| C++ process source | Dedicated non-login collector identity, no default capabilities | cn_proc initial namespace/kernel access; service hardening may change it | Interactive research access is not service access; report unavailable without escalation |
| C++ `/proc` context | Same least-privilege source identity initially | Own/other-user task visibility, executable/status reads, hidepid/ptrace/namespaces | Missing context stays missing; do not collect arguments/environment broadly or grant process-control capabilities by default |
| Journal source | C++ adapter with explicitly approved journal read access | Actual journal files/namespaces, possible broad journal-group exposure | Failed/system-only reads must be disclosed; broad group access is a privacy decision |
| Audit source | Existing read interface only, access explicitly reviewed | Existing log file ownership/read policy and rotation; no kernel stream ownership | Degrade if unavailable/inaccessible; a separately scoped privileged reader is an alternative requiring design, not an automatic root collector |
| IPC server/client | Python receiver and authenticated collector peers | Protected parent directory, exact UID/GID policy, socket creation/access and peer checks | No ordinary user may inject events or read frames; compromised authenticated collector can still lie, so validate semantics/limits |
| Python backend/writer/API | Separate non-login unprivileged service identity | SQLite/app-state write access, IPC receive, localhost API bind; no OS collection/log privileges | Compromise exposes/changes data and alerts it can access; do not give it collector/root capabilities |
| SQLite, sidecars, backups | Backend service access and root only | Candidate private directories 0700 and files 0600, including temporary/export paths | Collector/socket group must not gain DB access; no protection promised from compromised backend or root |
| Human dashboard | Root-only authorization; ordinary browser need not run as root | D-12a accepted: explicit UID-0 action per new session, including OS-authorized sudo; D-12b synthetic-only pilot accepted/tested; real-data integration pending | Localhost connection/interactive UID/research access is not dashboard authorization |
| Packager/service manager | Explicit privileged installation of HIDS-owned files/accounts/units only | Dedicated ownership, runtime/state directories and hardened service behavior | Separate future setup authorization; never changes PAM/journald/auditd settings or Audit rules |

Candidate IPC ownership: a Python-owned runtime directory with an approved ingest
traversal/connect group, no world access, and a socket limited to that group; keep
database directories outside it and backend-private. Exact modes (for example,
0750 directory / 0660 socket) are **review candidates**, not deployment commands or
approved policy. A root-owned protected parent can prevent an unrelated user from
substituting the service directory. Protect stale-socket removal against symlinks
and arbitrary paths. Peer identity must be checked in both relevant directions.

Do not combine collector read grants with backend database rights merely for
convenience. Whether source readers require isolated helpers/processes versus one
collector identity is D-01/D-10 work; installing a privileged helper expands the
attack surface and requires a narrow read-only protocol and separate review.

### Source-selection authorization and privacy gate

Discovery metadata, capability/permission results, source preferences and runtime
status are security data under the existing root-only policy. No initial event
collection begins before authenticated user confirmation. Only recognized HIDS
source choices may be submitted; reject arbitrary paths/commands and unconfirmed
start requests. Treat draft, confirmed and applied/runtime state separately and
validate stale/replayed control requests according to the approved policy (D-14).

Do not pre-collect a journal/proc sample or subscribe to demonstrate usability
without confirmation, even if no values are retained. Save only approved minimized
assessment/configuration information in private HIDS-owned storage; retention and
configuration records are not finalized here. Disabling/unselecting a source is a
HIDS operation, not permission to stop or reconfigure an OS logging service.

### Root-only browser authentication is a real design gate

A localhost TCP connection does not carry a usable root-user proof. A normal
browser cannot simply be treated as UID 0 because it runs on the same machine.
Owner D-12a now accepts explicit UID-0 authorization per new session, including
OS-authorized sudo; group membership alone grants nothing. The separate
[D-12b mechanism](dashboard-session-mechanism-review.md) is accepted for the
synthetic-only pilot and has [bounded acceptance](../validation/dashboard-session-pilot.md).
D-12c subsequently accepted the bounded selected-history view; [executed evidence](../validation/m4-history-view-acceptance.md). Broader routes, setup controls and production trust/lifecycle remain gated.

| Candidate approach | Benefit | Concern / decision needed |
|---|---|---|
| Root-authorized local broker/CLI proves UID 0 through a protected Unix interface, then grants a short-lived one-time browser bootstrap | Separates root approval from an unprivileged browser/backend; recommended direction for design review | Additional narrowly scoped component/protocol, one-time handoff, expiry/revocation and session security must be specified; no arbitrary privileged operations |
| Protected long-lived local bearer secret | Simple proof-of-possession mechanism to evaluate | Copying it into a normal browser exposes a reusable credential to that browser/account; storage, rotation, logging and authorization policy need review |

This table preserves the earlier options; D-12b separately selects the short-lived
root-authorized bootstrap for a synthetic-only pilot. Reusable credentials remain
excluded from URLs, process arguments, logs, exports and source records. The
accepted one-use URL-fragment handoff has its explicit browser/clipboard limits. Require
backend authorization for every sensitive endpoint; approve Host/Origin allowlists,
CSRF treatment, session expiry/revocation and cookie protections for the selected
mechanism. Do not launch a root browser or run the entire application as root.

A root-approved session in a normal browser does not isolate its bearer material
from compromise of that browser/account. Define that threat explicitly; do not
promise protection from same-account malware merely because the initial bootstrap
was root-authorized. Root compromise is outside the existing protection guarantee.

### Compromise and privacy implications

A compromised collector can leak native input it can read, forge events or exhaust
bounded ingestion; restrict its filesystem/capabilities and validate again in
Python. A compromised backend can expose/alter retained data, rules and alerts;
keep it away from privileged OS operations. Malicious source text may attack a
parser or web rendering; enforce limits and escape content. A compromised frontend
session can expose authorized security data, requiring revocation and bounded APIs.

The earlier ordinary-user system-wide cn_proc subscription shows a kernel-observation
path independent of HIDS. Root-only API/database protections do not block another
local process from independently observing whatever the tested kernel exposes.
This does not establish every account's access or executable/argument visibility.
Retained/enriched HIDS history still needs strict protection. Preserve the
[threat-model boundary](../threat-model.md#74-independent-process-observation).

## K. Collection-health model — proposal

Use separate **source capability/access**, **draft/confirmed source configuration**,
**initialization results**, **runtime collection**, **field availability**
and **transport/storage** observations. Avoid one overloaded green/red bit. The
[discovery states](../research/field-discovery.md#6-field-availability-classifications)
remain authoritative scoped concepts; user-facing phrases below do not replace
them or define a wire enum.

| User-facing situation | Required evidence / proposed explanation | Do not infer |
|---|---|---|
| Not selected / awaiting confirmation | Approved configuration has no confirmed active choice, or the UI has only a draft; no collectors started | Failure, health, or permission to initialize as a probe |
| Selected / initialization pending | User confirmed this HIDS source but runtime has not demonstrated usable operation | Selection equals success, a LISTEN ACK, or observed event delivery |
| Source available | Mechanism present plus actual identity's successful read/subscription evidence; record ACK and observed delivery independently | Permission for every identity, lossless future capture or health from an open descriptor alone |
| Source unavailable | Specific adapter cannot currently operate, with stage/reason/errno and freshness | A universal unsupported Linux capability |
| Access denied | Actual EACCES/EPERM or equivalent for identified source/identity | Feature absent, no relevant activity or permission to escalate |
| Collection interrupted | Adapter/connection stopped, fatal error or gap in known observation interval | Exact lost-event count or recovery of that interval |
| Events potentially lost / incomplete | ENOBUFS/overrun/truncation, parser rejection, queue overflow or other documented evidence | Every sequence gap is loss; a discontinuity count equals lost events |
| Source unsupported | Scoped documented build/protocol/platform evidence corroborating the failure | Unsupported solely from an inaccessible file/tracepoint or one generic check failure |
| Source not configured | Read-only inspection establishes a specific required existing mechanism/recording path absent/disabled; qualify sample scope | Empty event output proves not configured; permission failure proves absence; configuration may be changed automatically |
| No events observed | Sample window and last assessment/read state; distinguish no data, no matches, denied access and collector failure | No intrusion, working collection or no activity |

Each assessment should identify source/event role, actual service identity, collection
session, assessment time/freshness, last delivery when any, and bounded diagnostic
reason. Record monotonic versus wall clocks honestly, without turning absence of
activity time into a fabricated date. Before confirmation, use metadata/access evidence and documented/prior scoped
field information only; post-confirmation samples may establish observed fields.
Exact storage, refresh period, staleness thresholds and reconciling out-of-order
status updates remain D-10/D-14 decisions.

Map current adapter `unconfirmed`/`acknowledged`/`observing` and booleans into explicit
ACK/delivery facts. Its `degraded`/sticky incomplete interval and `unavailable`
notifications are inputs, not a fully implemented capability manager. Timeout is
not health success; `observing` means delivery happened, not a fresh safety verdict.
A new adapter session creates a new baseline, not a repair of previous gaps.

Keep source-local failures local. A failed journal source must not stop process
collection or authorized history access. An unavailable backend/database must be
reported through a bounded independent health path, with API/history availability
stated truthfully when those components themselves fail. Recovery needs fresh
access/continuity evidence and an explicit new state; do not erase old limitations.
No overall security/coverage percentage, numerical confidence score or automatic
qualitative confidence label is part of this health design.

##### Complete-but-uncommitted delivery acceptance cases

Test these distinct scenarios against the canonical addendum's durable registration,
interruption and finalization rules; none authorizes an invented acknowledgment API:

1. **Commit succeeded, acknowledgment lost.** Establish that the Python-owned SQLite
   transaction committed but its acknowledgment did not reach the sender. Reconcile
   against durable state. Any permitted retry uses the exact immutable, durably
   finalized delivery and deduplicates; no duplicate persistence or second execution
   event is allowed.
2. **Commit outcome uncertain.** Inspect authoritative durable SQLite state and
   transaction results through the approved ingestion boundary. Do not assume
   success or failure merely from the presence of an acknowledgment or error.
   Do not blindly retransmit payloads or assume an interrupted event can be
   reconstructed. A matching durable disposition must be established before retry
   or interruption handling could conflict with an already committed execution.
3. **Crash before durable finalization.** Establish that event progress was admitted
   and registered, but no durable finalization committed. Record the sanitized
   interruption disposition, discard unfinished payload, and suppress subsequent
   records for the interrupted identity. Never reconstruct it into an accepted event.

**Safety requirement:** if the correct durable disposition cannot be established,
stop or degrade the affected source rather than guess. Preserve the distinction
between durably finalized immutable retries, uncertain commits and interrupted
unfinished assembly. Exact protocol-3 reconciliation, response validation and
complete-but-uncommitted liveness remain **Evidence-dependent**; these acceptance
requirements do not settle the acknowledgment implementation or grant direct
SQLite access to the C++ collector.

**Evidence-dependent before code/native acceptance:** exact inactivity/lifetime and
pressure-stall durations; open-event/record/fragment/diagnostic/suppression limits;
ledger batching/write frequency and performance; range/coalescing storage overhead;
parser memory; rotation proof; reboot/reset; CPU/backlog/disk growth; storage thresholds;
SQLite/migrations; service IDs/permissions/endpoints; protocol-3 reconciliation/ACK
messages and actual filesystem accesses. No numerical tuning or runtime guarantees
are invented. Core availability remains ahead of M3 collection availability.

Preserve failure continuity, retention/migrations, bounded queues/memory/storage,

## Final recommendations

### Next three implementation tasks

Each requires a subsequent narrowly scoped implementation instruction; none is
executed by this review.

1. **Scope the M2 journal slice:** select the existing dataset, read permissions,
   native-to-normalized mapping and cursor/failure semantics under D-01–04/D-11.
2. **Implement M2 only after separate authorization:** reuse the accepted pipeline
   with scoped journal fixtures, read-only collection and bounded integration tests.
3. **Validate M2 on Ubuntu under the intended identity:** establish actual source
   access, source confirmation, rotation/replay and truthful failure/health behavior
   before proceeding to M3 source expansion. Install nothing by assumption.

M0/M1 are no longer future tasks. Later rules, API and UI follow the milestone
sequence above; authentication must be approved before exposing sensitive routes.

### Most significant architectural risks

- **Mistaking offline evidence for live readiness.** The Ubuntu build passes do not
  test actual connector delivery, source-account permissions, hardening or kernel
  cleanup. A successful temporary research run does not close those production gaps.
- **Timestamp/identity mistakes becoming durable.** Fabricated wall time or reused
  PID attribution could corrupt historical meaning and rule explanations; decide
  them before finalizing the shared contract.
- **A fragile boundary losing data invisibly.** Partial frames, ACK ambiguity,
  unbounded queues or blocked writer/enrichment paths can create hidden gaps and
  cross-source starvation. Keep errors/backpressure/health part of the first slice.
- **Root-only authorization with an unjustified credential handoff.** Loopback and
  an ordinary browser account do not prove root authorization; same-account session
  compromise and broker scope need explicit threat decisions before UI exposure.
- **Privileges expanding to fit missing sources.** Broad journal/Audit grants or
  an all-root service can expose more data than required. Unknown/inaccessible must
  remain valid outcomes rather than pressure to change logging or privilege policy.
- **Scope drift into v0.2.** History-based rules, fused authentication activities and
  evidence graphs can masquerade as normalization, enrichment or alert deduplication.
  Preserve one-event interfaces and exclude them from v0.1 acceptance tests.

### Blockers and safe work boundaries

There is **no blocker to this planning/documentation work**. There are concrete gates
before broader production work: real-source envelope/IPC/storage compatibility,
authentication before sensitive API/UI, privacy/source/account permissions
before live reads/deployment, and explicit dependency/setup approval when needed.
Confirmed-source control and measured resource acceptance are additional D-14/D-15
gates before live operation/release. M1's limited choices are approved and its
synthetic acceptance is complete; production extensions still need review.
No missing decision requires replacing the stack.

After a new implementation authorization, safe immediate work includes sanitized
fixture preparation, dependency-free/injectable context-reader tests, framing and
validator test harnesses against clearly labeled candidate contracts, and extending
offline regression coverage. Such work must not silently select final contracts or
handle real security data through an unauthenticated path. Already approved native
interfaces may be exercised offline without opening live sockets; no dependency or
host change follows automatically.

Owner approval is needed first for actual service identities/grants, privilege
boundaries, source/field retention policy, timestamp semantics, normalized/IPC/DB
contracts, rule semantics, root eligibility/authentication, retention/durability and
recovery guarantees. New dependencies, privileged installation and live experiments
also need explicit scoped authorization. Keep proposed plans separate from accepted
ADRs and measured validation, and record decisions when made.
